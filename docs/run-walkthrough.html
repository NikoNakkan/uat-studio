What it is

An Excel of test cases in, signed-off evidence out

The problem. User acceptance testing is usually a business person clicking through an Excel of test cases by hand, a few hours per round, with screenshots pasted into a document. Every new version of the app means doing it all again.

What UAT Studio does. You upload the same Excel. AI agents make the cases precise, walk them in the real app, and write a Playwright test for each one. From then on the tests run without AI: fast, repeatable, with a screenshot of every step and a full trace. When something fails, an agent explains why and checks it again before calling it a bug. A person signs off, and the result is a sealed results.xlsx.

The two parts. The kit (kit/) is the engine: the stage list (config/workflow.yaml), the agents' instructions, the skills with their scripts, the rules and templates. UAT Studio is the app around it: the screens, the live panel, projects, costs, settings. The kit also runs on its own in VS Code with GitHub Copilot; Studio drives the same engine.

Getting it runningA new machine needs Python and Node.js, then one command: install.ps1 (Windows) or install.sh (macOS, Linux) installs the packages, builds the app, and installs Playwright and Chromium. Start Studio, open it, and Set up does the rest. The kit comes inside the repository (kit/).
The one sentence for the demo"The AI does the slow, clever part once (understanding the cases and writing the tests); after that, testing a new version is a button, and a person still makes every decision that matters."

Set up

Once per app, all in the app: who runs the AI; the app under test: the start page and allowed site (taken from the Excel's Start page column when none is set), then this machine (Node, Playwright, Chromium, Python, all checked, with one Fix everything); and test accounts: first how the tests log in (an agent writes it once and proves every account logs in), then the accounts (the Excel's "Login as" names are listed, you type only the passwords, never shown again, never sent to the AI). No .env anywhere: Studio keeps these values itself and hands them to the tests while they run.

Guardrails

What agents may never do: sites the browser may open, words that make it ask you before clicking (delete, remove, send, pay), names it never clicks, blocked tools, files nobody may open (.env always), and whether accepting a browser dialog asks you. Checked before every agent action.

Knowledge

The project's glossary (the app's words with one meaning each), the app map the planner builds, the rules files, the test files, the agents and skills of the kit, read-only or editable.

Feature switches

Every part of the flow can be switched off (for example the live app check, flakiness runs or the screen reviewer); what depends on it switches off with it and the page says what you lose.

Settings

Who runs the AI: an Anthropic API key (exact token costs) or GitHub Copilot (your plan; a fine-grained token with Copilot Requests, or the GitHub CLI's sign-in; company seats work too). The model per agent, run limits, showing the browser, the kit's self-tests.

Projects

Top of the sidebar: one project per app under test, each with its own kit folder, rules, runs and settings for costs and baseline. Switching is per browser tab.

The flow

One run, start to finish

Check the setup ─▶ Read the Excel ─▶ Clarify ◀──────────────┐ steps that cannot be done │ │ (max 2 rounds) ▼ │ Write the plan ─▶ Check steps in the live app │ ▼ ┌──────────▶ Write the tests ─▶ Check the tests ─┐ │ rejected (max 2 attempts per case) │ └────────────────────────────────────────────────┘ │ ▼ Run the tests (no AI) ─▶ Explain failures ─▶ Compare screens ─▶ Sign off ─▶ results.xlsx

Who decides what happens next: code, not AI. Studio walks config/workflow.yaml stage by stage and saves where it is in progress.json, so a stopped run resumes where it stopped. Each AI agent is its own conversation with only the tools its job needs; it cannot call another agent or skip a step. Agents share nothing except the files they leave in the run folder.

The second run of a pack is much cheaper. The Excel is compared with the last signed-off run: unchanged cases reuse their tests, only new or changed ones go through clarify, the live app check and writing. A test that already exists is never written again without asking you.

    Loops

    Where the flow goes back

    Check steps in the live app → Clarify the cases

    Steps that do not match the real app (a button with another name, a missing page) go back to the clarifier as questions for you, then the plan is rewritten and checked again. At most 2 rounds (max_planner_rounds).

    This run: no mismatches, so no round. On the run page, Clarify shows as running again with "Round 2, from the live app check" while it happens.

    Check the tests → Write the tests

    A test the check rejects goes back to the generator with the reasons. At most 2 attempts per case (max_generate_attempts); a case still rejected after that is reported at sign-off.

    This run: TC-15 went back once. The check said "the check does not contain 'Paracetamol 6 on hand'"; the second version was accepted and passed 3 repeat runs.

    When it asks you

    A person decides only what needs judgement or accountability

    It asks youWhy a person
    Confirm a changed case (reuse its test or write it again) and any new case that already has a testOnly the author knows whether the change matters to the old test; rewriting a good test (or one that found a bug) wastes time.
    Clarifying questions about unclear steps or results (as strict as you chose: basic, standard or strict)The Excel is the requirement; the AI must not invent values. Each question comes with a recommended answer, and you can export them as a questionnaire for the Excel's author.
    Before clicking delete, remove, send or pay, and before accepting a browser dialogThose actions change data or reach the outside world; the guard stops and asks.
    Whether a broken test may be repairedA repair changes a test that was accepted; you decide, and the lock makes sure it still checks the same things.
    Sign-off: PASS, CONCERNS, FAIL or WAIVED per group, and the result of each manual caseAccountability. The AI recommends from the evidence; a named person decides, and a WAIVED needs who and why.
    Set up: installing something, writing the loginIt changes the machine or uses the test accounts.
    It never asks youWhy not
    Whether the app or the test case is right when the app shows something elseThe Excel is the requirement and the tester cannot know more. The test is written as the Excel says, fails, and the diagnosis confirms the bug with evidence. Asking would let a wrong answer hide a bug.
    Reading the Excel, writing the plan, checking and running the tests, comparing screensDeterministic scripts with fixed rules: there is nothing to decide.
    Whether a failure is a bug or a broken testThe diagnostician reads the error, screenshots and trace and reproduces it; you see its verdict and evidence at sign-off and can still decide otherwise.
    Every step an agent takes in the browserThe guard already refuses what is forbidden and asks only for the risky clicks; asking for every click would make automation pointless.
    Why not ask about everything?Every question costs a person's time and stops the run. Studio asks only where a wrong guess would cost more than the question: a value the AI would otherwise invent, an action that cannot be undone, a test that would be thrown away, and the final decision someone must answer for. Everything with fixed rules runs by itself, and anything you leave unanswered simply waits.
    Pass, concerns, fail

    What sign-off recommends, and why

    SituationRecommended
    Passed, with a real check for every expected result, a screenshot for every step and a tracePASS
    Passed but evidence is missing (a screenshot, a check, the trace)CONCERNS, naming what is missing
    Failed, diagnosed app broken, reproducedFAIL
    Failed, app broken, could not reproduce (or already fixed)CONCERNS
    Failed, test broken (the app was not judged)CONCERNS: repair the test and run again
    Failed because of the environment (network, the app was down)CONCERNS: not counted against the app
    A manual case (Automation = manual)MANUAL: the person records PASS, FAIL or NOT_RUN, who did it and where the proof is

    A group takes its worst case (FAIL over CONCERNS over PASS). Sign-off seals the run: every evidence file is fingerprinted in manifest.json, and results.xlsx can only come from those files. Redo sign-off clears the decisions and keeps the old ones in the run.

    Safety

    Why an AI clicking around a real app is safe

    • The guard checks every agent action before it happens: only the allowed sites, no blocked tools, never the private files, and it asks before delete, remove, send, pay and dialogs.
    • No code in the page: browser_evaluate is blocked, because the guard cannot see what code does; agents act like a user, through clicks and typing.
    • Passwords never reach the AI, or the project folder. Studio keeps them in its own settings folder and hands them to the tests only while they run, as environment variables; the tests log in through tests/login.ts, which receives them as arguments; the login check removes them from any output before anyone sees it.
    • Page text is data, not instructions. Agents are told so, and the planner's findings only count when they name a real Test ID of the run.
    • Tests cannot cheat: the test check rejects tests that fake the server, run code in the page, skip steps, wait blindly or never check anything.
    • On Copilot, each agent session has only Studio's own tools: Copilot's built-in shell and file tools are off.
    Cost

    What it costs, and what it saves

    • The first run of a pack is the expensive one: every case is walked and written. The first Lumen run (36 tests) was about $14 by list prices, really about $10 with caching.
    • Later runs reuse the tests: the v3 run (2 new or changed cases) cost about $1.21. Running the tests themselves never costs AI.
    • On GitHub Copilot it counts premium requests instead: one per message to an agent (its own tool calls do not count again), from your plan's monthly allowance.
    • Costs saved on Home compares every run with a person testing by hand at your hourly rate.

    2. Start Studio: cd backend, .venv\Scripts\python -m app (http://127.0.0.1:8765).
    3. Settings: the provider you will use; press Test. On Copilot check the premium requests left.
    4. Set up shows everything green (machine, start page, both test accounts, login written). In a new project: create it from the sidebar's project menu, type the two passwords on Set up (Employee: employee@lumen.test, Manager: manager@lumen.test, passwords in demo-app/README.md), and let Set up write the login; the start page comes from the Excel.
    5. Have demo-app/uat/lumen-clinic-demo-10.xlsx at hand. For a first run use a new project, so all 10 tests are written live; in an existing project most tests are reused and the run is short.
    1. The problem (1 min). Open the Excel: 10 cases in plain business language, the way testers receive them. "Today someone clicks through these by hand, every release."
    2. Start the run (1 min). Test runs → New run → the Excel → standard questions → Start. Point at the stepper and the live panel.
    3. Clarify (2 min). The clarifier asks a few questions with recommended answers; answer one, mention Export questionnaire for when the author is someone else.
    4. The live app (3 min). Show the browser the agent drives (Settings → show the browser). The planner walks each case; the generator writes a test per case. Open a test file under Write the tests: readable Playwright code, a comment per Excel step, a screenshot per step.
    5. Quality gate (1 min). Check the tests: every test checked against the rules and run 3 times. If one went back (yellow "1×" arc), say why.
    6. Run, no AI (1 min). All tests run in about a minute. Expected: 6 pass (TC-01, 03, 04, 21, 25, 43), 4 fail (TC-39 billing, TC-40 search, TC-41 notes, TC-42 stock).
    7. Why they failed (3 min). Open Explain failures: each one "app broken, reproduced", with what was expected, what happened and why. Open TC-41's evidence: Ada's note on Alan Turing's page, a patient-safety bug a hurried manual tester could miss.
    8. Sign-off (2 min). The recommendations (FAIL for the bug groups), decide, close, download results.xlsx.
    9. The payoff (1 min). Home: Costs saved; the run's cost. "Next release: same Excel, the tests are reused, the run takes minutes."
    If something goes wrong A test errors with "connection refused": the clinic app is not running. · Set up not green: open Set up, follow the red step. · A question waits forever: the sidebar's "1 waiting for you" opens it. · Copilot answers with another model: the plan does not include that model (Opus is not in Copilot Pro); it still works, on Sonnet. · Everything passes: the clinic app running is not the copy with the bugs.
    Questions

    What people tend to ask

    Does the AI decide whether the release passes?

    No. It recommends from evidence with fixed rules (above); a named person decides every group, and a waiver needs a reason.

    What if the AI writes a test that always passes?

    The test check rejects tests without a real check for each expected result, tests that skip, wait blindly, fake the server or run code in the page; new tests must pass 3 runs in a row. Sign-off also refuses a PASS without a screenshot for every step.

    What if the app changes its buttons?

    The failing test is diagnosed as test broken; you can approve a repair by Playwright's healer, which is locked from changing what the test checks. Or rerun the case through generation.

    What does it cost per release?

    The first run of a pack pays for writing the tests; later runs only for new or changed cases (the v3 run: about $1.21). Running the tests is free. Or use a GitHub Copilot plan.

    Can it test our real systems?

    Any web app the browser can reach, including Power Apps canvas apps (a specialist agent maps them). The guardrails limit it to the sites you allow; test accounts, never real users' data.

    Where does our data go?

    Runs, evidence and passwords stay on the machine. The AI sees the test cases, the app's pages as the agent walks them, and the evidence it reviews; never the passwords.

    Why not let the AI just test everything itself, with no Excel?

    Acceptance is about what the business agreed. The Excel is that agreement; the AI's job is to test exactly it, and to say clearly when the app does something else.

    What happens with a manual case (a phone call, an email)?

    It is never automated; the run lists it, and at sign-off a person records the result, who did it and where the proof is. The sign-off cannot close without it.
